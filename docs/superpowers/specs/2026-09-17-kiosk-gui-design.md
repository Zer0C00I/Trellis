# Kiosk GUI (Slint) — Design Spec

Дата: 2026-09-17
Статус: approved after brainstorming, pre-implementation
Spec, от которого наследуется: `docs/superpowers/specs/2026-09-12-family-vault-design.md`
On-chain программа, к которой обращается этот GUI: `family-vault` (core +
approvals планы, оба реализованы и прошли финальный review — см.
`docs/superpowers/plans/2026-09-12-family-vault-core.md` и
`docs/superpowers/plans/2026-09-12-family-vault-approvals.md`)

## Цель

Native Rust GUI-приложение на Slint — единственное, что видит пожилой
человек на устройстве. Не браузер, не dApp-клиент, не имеет доступа к
произвольным URL. Показывает баланс, позволяет отправить деньги
заранее одобренным получателям (closed address book — см. родительский
spec), и ничего больше.

## Аудитория и когнитивная модель

Целевой пользователь — человек 70+, возможно с лёгкими когнитивными
нарушениями (не диагностированная деменция, но замедленная обработка
информации, сниженная зрительная острота, тремор/сниженная мелкая
моторика). Дизайн ориентируется на evidence-based рекомендации по
интерфейсам для пожилых и людей с когнитивными нарушениями, не на
интуицию дизайнера — источники ниже.

Ключевой принцип из исследований: **упрощение — не значит
примитивизация**. Урезанная до костей версия провоцирует БОЛЬШЕ ошибок,
не меньше, потому что не даёт достаточно контекста для уверенного
действия (Smart Interface Design Patterns — Designing For People With
Dementia). Цель — убрать когнитивную нагрузку (жаргон, лишние шаги,
неочевидные состояния), не убрать функциональность.

## Стандарт доступности — WCAG 2.2, целевой уровень AAA

Полный текст стандарта сохранён локально:
`docs/references/wcag22.html` / `docs/references/wcag22.txt`.

W3C официально не рекомендует требовать AAA как политику для "entire
sites", потому что не для всякого контента это физически достижимо
(Understanding WCAG 2.0, Conformance). Это приложение — узкое,
single-purpose, без медиа-контента и гиперссылок — именно тот случай,
где AAA реалистичен. Полный обзор всех 30 AAA-критериев ниже.

### Неприменимо (в приложении нет такого контента)

1.2.6–1.2.9 (аудио/видео-медиа), 1.4.7 (фоновый звук), 2.4.9 (Link
Purpose — гиперссылок нет), 2.1.4 (Character Key Shortcuts — нет
полноценной клавиатуры).

### Применяется напрямую

| Критерий | Требование | Как выполняем |
|---|---|---|
| 1.4.6 Contrast Enhanced | 7:1 обычный текст, 4.5:1 крупный | Фиксированная высококонтрастная цветовая тема, проверяется вручную при вёрстке каждого экрана |
| 1.4.8 Visual Presentation | Разумная ширина строки, не justify | Короткие подписи, левое выравнивание |
| 1.4.9 Images of Text | Не использовать текст-как-картинку | Slint рендерит реальный текст, не растровые подписи |
| 2.3.2 / 2.3.3 | Нет мельканий >3/сек, анимации отключаемы | Минимум анимации, никаких морганий/спиннеров-миганий |
| 2.4.8 Location | Понятно, где ты | Крупный заголовок экрана = "где я" |
| 2.4.10 Section Headings | Заголовок на каждом экране | То же |
| 2.2.4 / 2.2.5 / 2.2.6 | Нет форс-таймаутов, нет незапрошенных прерываний | Экраны не переключаются сами (кроме экрана результата — см. ниже, с запасом времени, не прерывает середину действия) |
| 2.4.12 / 2.4.13 Focus | Focus indicator виден и не перекрыт | Slint focus-chain, видимая рамка на активной кнопке — нужна для клавишной навигации (см. 2.1.3 ниже) |
| 2.5.5 Target Size Enhanced | 44×44px минимум | Берём с запасом: **60×60px, отступ между кнопками 16px** (эмпирически: снижает ошибки нажатия на ~70% против 44px — см. Sources) |
| 2.5.6 Concurrent Input | Не блокировать другие модальности ввода | Тач ИЛИ физические кнопки — оба всегда доступны, не эксклюзивны |
| 3.1.3 / 3.1.4 / 3.1.5 / 3.1.6 | Простой язык, без жаргона, уровень чтения ≤ средняя школа | **Запрещённые слова на экране**: "tx hash", "PDA", "confirmed on-chain", "wallet address", "seed", "gas", "network fee". Разрешено: имена людей, суммы в валюте, "Готово"/"Не получилось, попробуй ещё раз" |
| 3.2.5 Change on Request | Экран не меняется без действия пользователя | Переходы только по тапу/нажатию, кроме автовозврата на экране результата |
| 3.2.6 Consistent Help | Кнопка помощи в одном месте везде | "Позвать [имя родственника]" — фиксированное место на каждом экране (нижний правый угол) |
| 3.3.6 Error Prevention (All) | Подтверждение для любого действия с последствиями | Экран подтверждения перед каждой отправкой — единственное действие с последствиями в приложении |
| 3.3.9 Accessible Authentication Enhanced | Ноль когнитивных тестов на вход, без исключений | Нет логина вообще — проходит тривиально (унаследовано из threat model родительского spec) |

### Честное исключение — 2.1.3 Keyboard (No Exception)

Требует полной операбельности с клавиатуры без исключений. У устройства
нет QWERTY-клавиатуры. **Решение**: 3-4 физические кнопки на реальном
железе (например Вверх/Вниз/Выбрать/Назад), замапленные на Slint
keyboard focus events (`FocusScope`, `key-pressed`) — та же модель, что
у пульта телевизора или switch-access устройства. Это не полная
QWERTY-клавиатура, но it's a legitimate "keyboard interface" в смысле
WCAG (последовательная навигация фокусом + активация), поэтому 2.1.3
выполняется по духу, не только по фиктивной формальности.

Для dev/демо на десктопе: мышиный клик = тач-тап, работает из коробки
через `winit`-backend Slint, дополнительного кода не требует.

## Экраны

### 1. Мой кошелёк (главный экран, домашний)

- Крупно: баланс personal vault (число + валюта, с разделителями
  разрядов — без них числа хуже читаются, особенно у пожилых
  пользователей со зрительными нарушениями)
- Список получателей (`BeneficiaryList` с бэкенда) — по одной крупной
  кнопке на каждого, имя крупным шрифтом, без адресов/технических
  деталей
- Кнопка "Семейный кошелёк" — отдельная, визуально отличается (другой
  цвет/иконка), ведёт на Экран 5
- Кнопка помощи — фикс. позиция (низ, правый угол)
- **Не показываем**: баланс пула на этом экране (см. решение
  "разделение экранов" из brainstorming — два числа на одном экране
  создают неоднозначность "какое моё")

### 2. Выбор суммы

- Открывается после тапа по получателю на Экране 1
- Заголовок: "Сколько отправить [Имя]?"
- 2-4 preset-кнопки с суммами (заданы родственником через отдельный
  интерфейс — не на этом устройстве, см. родительский spec:
  "family premium subscription" даёт родственнику доступ к настройке)
- **Нет** цифровой клавиатуры/свободного ввода суммы (evidence-based
  решение — см. Sources)
- Кнопка "Назад" — фикс. позиция

### 3. Подтверждение

- Обязателен по WCAG 3.3.4/3.3.6 — не пропускаем ни при каких
  обстоятельствах
- Крупно: "Отправить [Сумма] → [Имя]?"
- Две кнопки, одинакового размера, чётко разделены: "Отправить" /
  "Отмена" — не делаем одну кнопку визуально доминирующей (это подтолкнёт
  к непреднамеренному подтверждению)
- Пока идёт транзакция (несколько секунд на devnet) — простой
  индикатор ожидания, без технического текста ("Подожди немного...")

### 4. Результат

- Крупная иконка (✓ успех / ✗ неудача) + простой текст:
  "Готово! Деньги отправлены [Имя]" или "Не получилось. Попробуй ещё
  раз или позови [родственника]"
- Автовозврат на Экран 1 через 5-8 секунд — но только после того, как
  результат уже показан и действие завершено (не прерывает что-то
  незавершённое — соответствует 2.2.4/3.2.5)
- Кнопка "Ок" доступна сразу — не обязательно ждать таймер

### 5. Семейный кошелёк

- Тот же паттерн, что Экран 1, но для pool vault: баланс пула,
  получатели, суммы
- Кнопка "Назад к моему кошельку" — фикс. позиция (та же, что кнопка
  "Семейный кошелёк" на Экране 1, для консистентности — 3.2.4)
- Withdraw из pool vault может тем не менее пойти по over-limit
  ветке (`request_withdrawal` вместо прямого `withdraw`) — это
  **прозрачно для пользователя**: экран/кнопки идентичны, разница
  обрабатывается клиентским кодом (сравнение с `daily_limit`/
  `spent_today`, прочитанными с аккаунта), не показывается как отдельный
  "сложный" флоу на экране

## Технологический стек

Подтверждено родительским spec: Slint (`i-slint-backend-winit`, feature
`backend-winit-wayland` для реального железа, дефолтный winit-backend
для dev/demo на десктопе), GPLv3.

- **Клиент блокчейна**: `solana-client` + `solana-sdk`/гранулярные
  крейты — версия фиксируется отдельно при реализации (может не
  совпадать с версией внутри программы/тестов, см. родительский spec's
  "Технологический стек")
- **Signer**: локальный зашифрованный keypair, как описано в
  родительском spec's разделе "Signer / хранение ключа (MVP threat
  model)" — то же ограничение (защищает от UI-based атак, не от
  физической кражи устройства с root-доступом), то же смягчение
  (closed address book ограничивает ущерб)
- **Чтение состояния**: `Vault`/`BeneficiaryList` deserialize через
  `anchor_lang::AccountDeserialize`, тот же паттерн, что уже
  используется в litesvm-тестах программы — переиспользуем знание
  layout аккаунтов, не изобретаем заново

## Data flow (упрощённо)

```
Slint UI thread
  │  (клик по кнопке)
  ▼
Application logic (Rust, вне UI-потока)
  │  строит Instruction (family_vault::instruction::Withdraw {...})
  │  или family_vault::instruction::RequestWithdrawal {...}
  │  если amount не влезает в оставшийся daily_limit (только для pool)
  ▼
Подписывает локальным keypair
  ▼
solana-client RPC → devnet
  ▼
Результат (Ok/Err) → обратно в UI-поток → Экран 4
```

## Обработка ошибок

- Любая ошибка RPC/транзакции → Экран 4 в состоянии "неудача", простой
  текст без деталей ошибки в UI (технические детали — в лог-файл на
  устройстве, для отладки родственником удалённо, не на экране)
- Таймаут RPC (нет сети) → отдельное, тоже простое сообщение:
  "Нет связи. Попробуй ещё раз позже" — не путать с "Не получилось"
  (транзакция реально не прошла) — эти два случая различаются в логике,
  не только на экране

## Открытые вопросы / вне скоупа этого spec

- Точная цветовая палитра (конкретные hex-значения, проверенные на
  7:1 контраст) — определяется при реализации, не блокирует spec.
- Прошивка 3-4 физических кнопок (GPIO на Raspberry Pi → keyboard
  events) — отдельный вопрос для Alpine/cage-плана, не для этого GUI-spec.
- Настройка preset-сумм родственником — отдельный интерфейс/приложение,
  не входит в этот kiosk GUI (см. монетизация в родительском spec:
  "family premium subscription").
- Локализация/язык — предполагается один язык на устройство, выбранный
  при настройке; мультиязычность не в MVP.
