# Kiosk First-Run Setup — Design Spec

Дата: 2026-09-23
Статус: approved after brainstorming, pre-implementation
Spec, от которого наследуется:
`docs/superpowers/specs/2026-09-12-family-vault-design.md` (threat model,
closed address book, anti-scam модель),
`docs/superpowers/specs/2026-09-17-kiosk-gui-design.md` (экраны, WCAG/ETSI
copy-конвенции),
`docs/superpowers/specs/2026-09-21-kiosk-blockchain-wiring-design.md`
(`ChainConfig`, `chain.rs`, error-mapping паттерн)

## Цель

Устройство продаётся бабушке уже с прошитым образом. На нём нет
приватного ключа, нет vault'а, нет `kiosk.toml`. Первое включение должно
само: сгенерировать ключ-владельца, показать его публичную часть
родственнику (через QR — единственный практичный канал без клавиатуры и
без действий от самой бабушки), дождаться финансирования и
самостоятельно создать personal vault. Без единого секрета, введённого
человеком, и без стороннего провижининг-инструмента (`admin-cli` тут не
участвует вообще — весь flow внутри `kiosk-gui`).

## Почему не отдельный setup-бинарник

Рассматривались два подхода: (a) отдельный `kiosk-setup` бинарник,
запускаемый один раз перед `kiosk-gui` (например через systemd unit,
"если нет kiosk.toml — сначала setup, потом exec kiosk-gui"), (b) новый
`Screen::Setup` внутри уже существующего `kiosk-gui`. Выбран (b):

- Не нужен второй процесс/systemd-оркестрация — меньше движущихся частей
  на реальном железе (см. будущий Alpine/cage план — там и так есть
  вопрос автозапуска, не хочется добавлять туда ещё и цепочку из двух
  бинарников).
- Переиспользуется уже готовый `AppWindow`/тема/стиль — QR-экран
  визуально та же кисок-эстетика (чёрно-белая, крупный шрифт), не
  отдельное окно с своим стилем.
- После успешного setup — просто `set_current_screen(Screen::MyWallet)`
  в том же процессе, без перезапуска.

## Файлы на устройстве

| Путь | Кто создаёт | Содержимое |
|---|---|---|
| `/etc/family-vault/provisioning.toml` | Прошивка образа (build-time, до продажи) | `rpc_url`, `program_id`, `mint` — **публичные**, без секретов |
| `/etc/family-vault/owner-keypair.json` | kiosk-gui, при первом запуске | Сгенерированный keypair, `0600`, root-owned |
| `/etc/family-vault/kiosk.toml` | kiosk-gui, **только после** успешного `initialize_vault` | Полный `ChainConfig` (тот же формат, что уже читает `chain::load_config`) |

`provisioning.toml` — намеренно отдельный, более узкий файл (не
`kiosk.toml` с пустыми полями): в нём физически невозможно случайно
захардкодить чувствительные значения при прошивке образа, потому что в
нём нет полей для vault-адресов и keypair-пути вообще.

## Определение "нужен ли setup"

При старте `main()`: если `kiosk.toml` (по обычному пути/`--config`)
**не существует** — режим setup. Если существует — обычный режим,
поведение не меняется (уже реализовано).

Внутри setup: если `owner-keypair.json` уже существует на диске — он
**переиспользуется** (не перегенерируется). Это даёт восстановление
после сбоя питания посреди setup: pubkey уже показан в QR, родственник
уже мог начать перевод SOL — потеря этого прогресса при перезагрузке
была бы реальной проблемой.

## Экран Setup

Один новый `Screen::Setup` в `app.slint`. Контент:

- Заголовок: "Настройка устройства" (или похожее, финальная формулировка
  проверяется по plain-language правилам из ETSI EG 203 350 — короткие
  предложения, без жаргона, как и остальные экраны)
- QR-код (генерируется в Rust, растровое изображение)
- Статус-текст под QR, меняется по мере прогресса:
  - "Покажите этот код родственнику, у которого будет доступ к
    приложению семьи"
  - (после начала фонового опроса) "Ожидаем подтверждение..."
  - (после фандинга, во время отправки init-транзакции) "Почти готово..."
- Никаких кнопок на этом экране — процесс полностью автоматический,
  нет действия, которое могла бы (или должна) совершить бабушка.
- Никакой мигающей анимации (WCAG 2.3.2/2.3.3, уже действующее
  ограничение проекта) — только смена статус-текста.

## QR-генерация

Крейт `qrcode` (чистый Rust, без сетевых/системных зависимостей).
Строит матрицу модулей → растрируется в `Vec<u8>` RGB8 (чёрный/белый,
без anti-aliasing — QR должен остаться машиночитаемым) → оборачивается в
`slint::SharedPixelBuffer<Rgb8Pixel>` → `slint::Image::from_rgb8(...)`.
Кодируемая строка — просто base58 pubkey (`owner.pubkey().to_string()`),
никакого кастомного URI-схема пока не нужно: family app просто парсит
raw base58 из QR.

## Фандинг и самостоятельная инициализация

Фоновый поток (тот же паттерн `std::thread::spawn` +
`slint::invoke_from_event_loop`, что уже используется в `chain.rs`):

1. `loop { rpc.get_balance(&owner_pubkey); if balance >= MIN_LAMPORTS { break } sleep(4s) }`
   — `MIN_LAMPORTS` берётся с запасом над стоимостью
   `initialize_vault` (rent за `Vault`+`BeneficiaryList`+ATA + fee) —
   точное число фиксируется на этапе реализации через
   `rpc.get_minimum_balance_for_rent_exemption`, не жёстко хардкодится
   произвольным числом.
2. Как только профинансирован: строит `InitializeVault` инструкцию
   (`is_pool = false`, `daily_limit` не важен для personal — тот же
   паттерн, что уже в `admin-cli::cmd_create_vault`, но здесь **payer =
   owner = один и тот же ключ** — устройство платит само себе).
3. При ошибке отправки (RPC недоступен, транзакция отклонена) —
   **не блокируется навсегда**: статус-текст меняется на "Не получилось,
   пробуем ещё раз" и петля продолжает опрашивать баланс/пересобирать
   попытку (тот же баланс уже есть, повторная попытка идемпотентна —
   `initialize_vault` с `init`-констрейнтом на уже существующий PDA
   просто откажет как "уже существует", это трактуется как успех, не
   как ошибка).
4. При успехе: пишет `kiosk.toml`. Поля `pool_vault`/
   `pool_beneficiary_list` временно равны `personal_vault`/
   `personal_beneficiary_list` (тот же placeholder-паттерн, что уже
   используется вручную в текущем `kiosk.toml` — Family Wallet будет
   показывать те же данные, что и My Wallet, пока family app не создаст
   отдельный pool vault; это не отдельный код путь, просто одинаковые
   значения в конфиге).
5. `set_current_screen(Screen::MyWallet)` + сразу вызывает уже
   существующий `refresh_vault_state(...)` с новым `cfg` — без
   перезапуска процесса.

## Обработка ошибок

- `provisioning.toml` отсутствует/битый → это ошибка прошивки, не
  восстановимая на месте — показываем понятный текст ("Обратитесь в
  поддержку") и не пытаемся угадывать дефолты.
- RPC недоступен во время poll — просто продолжает попытки (баланс не
  может уменьшиться сам по себе, ждать безопасно, никакого таймаута не
  нужно — устройство и так простаивает до продажи).
- `initialize_vault` откладывается ошибкой, отличной от "уже существует"
  (например, невалидный `mint` из `provisioning.toml`) — после N неудачных
  попыток (фиксируется на этапе реализации, например 5) переходит в
  постоянное состояние ошибки с текстом "Не получилось. Обратитесь в
  поддержку" — не крутит бесконечный молчаливый retry без обратной связи.

## Тестирование

- Юнит-тесты (без сети) в новом `kiosk-gui/src/setup.rs`: генерация QR
  из известного pubkey (проверка размеров растра/детерминированности),
  round-trip keypair generate-then-reload с диска, `needs_setup()`
  логика (есть файл / нет файла).
- Реальная проверка на devnet (как и для blockchain-wiring plan) —
  вручную: стереть `kiosk.toml`, запустить с реальным
  `provisioning.toml`, вручную профинансировать показанный на QR pubkey
  с помощью `solana transfer`, убедиться что vault создался и экран
  переключился сам.

## Открытые вопросы / вне скоупа

- Настройка WiFi/сети на первом запуске — предполагается, что
  устройство уже подключено (ethernet или предустановленный WiFi) до
  первого включения; отдельная задача, не в этом spec'е.
- Создание pool (family) vault — отдельный шаг со стороны family app,
  не в этом flow.
- Реальное шифрование `owner-keypair.json` (TPM/secure element на
  реальном железе) — вне скоупа, тот же MVP threat model что уже
  документирован в родительском spec (`0600`, root-only, защищает от
  UI-атак, не от физического root-доступа).
- QR не содержит ничего кроме pubkey — если позже понадобится передать
  больше данных (например rpc_url, чтобы family app точно знал на какой
  кластер смотреть), потребуется расширение формата — не в этом spec'е.
